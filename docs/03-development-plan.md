# 开发计划

## 1. 交付策略

先交付“安全、只读、可运营”的 MVP。Bot 只展示 `new-api` 的最小实时摘要，不扩展到兑换、支付、订单、令牌或额度写操作。

以下工期按 1 名熟悉 TypeScript、Telegram Bot 和 Docker 的开发者估算，是合理推测，不是固定承诺。联调环境、产品文案和部署权限缺失会延长工期。

## 2. 阶段计划

> 当前代码已完成阶段 1-4 的可运行基础：原生官方 `admin` 模式下的绑定核验、账户/用量/订阅读取、公开模型目录、通知偏好与幂等通知 Worker、公告、客服路由和带二次确认的管理员广播。`bridge` 仅是可选扩展。Redis/BullMQ 不是当前 MVP 的运行前提；前期使用 SQLite 与进程内定时器，规模扩大后迁移 PostgreSQL 并增加独立 Worker/队列。

| 阶段 | 工作内容 | 产出 | 估算 |
| --- | --- | --- | --- |
| 0. 范围与接口冻结 | 确认角色、功能、语言、规模、`new-api` URL/版本和是否允许扩展 | 决策记录、接口样例、验收清单 | 1-2 人日 |
| 1. 工程基础 | TypeScript、Fastify、grammY、配置、日志、SQLite、CI、Docker | 可部署空服务、Webhook、健康检查 | 2-3 人日 |
| 2. Bridge 与账户查询 | `new-api` 只读 Bridge、HMAC、Telegram ID 解析、账户摘要、额度换算 | 无 UID 手工输入的核心闭环 | 4-6 人日 |
| 3. 用量与订阅 | 今日/7/30 天统计、订阅展示、异常归一化 | 完整只读自助菜单 | 2-3 人日 |
| 4. 通知与客服 | 额度/到期通知、去重、客服群转发与回复 | Worker 与运营闭环 | 3-4 人日 |
| 5. 广播与管理 | 管理员白名单、广播预览确认、限速、失败追踪 | 运营功能 | 2-3 人日 |
| 6. 加固与上线 | 契约测试、E2E、压测、监控、备份恢复、运行手册 | MVP 正式发布 | 3-4 人日 |
| 7. TG 易支付充值 | 加固 `new-api` Epay 原子入账，增加 scoped Bridge、checkout URL/二维码和 Bot 状态查询 | 本地实现与 focused contract 已完成；服务商沙箱验收待做 | 14-25 人日 |

当前 Node MVP 骨架已完成，含 admin 临时联调模式；完整 Bridge + 运营 MVP 预计约 18-27 人日，通常是 1 名开发者 4-6 周。若暂时不做客服和广播，可压缩到约 13-18 人日。

兑换和令牌管理不在本项目计划内。Telegram 易支付充值的本地实现已完成；设计、测试矩阵和外部验收前置条件见 `docs/05-telegram-epay-topup-plan.md`。在服务商沙箱验收前继续由 `new-api` 网页处理。

## 3. 每阶段完成定义

### 阶段 0：范围与接口冻结

- 获取测试环境和一个普通用户、一个专用管理员测试账号。
- 记录 `new-api` 版本或 Git commit，不以“最新版”作为接口契约。
- 用真实响应生成脱敏 fixture，确认账户、日志、订阅和错误格式。
- 决定首版语言、时区、额度显示、通知频率和客服群。
- 确认正式环境是默认 `admin` 只读模式，还是已具备并启用 Bridge 的实例；前者必须按高权限 Admin PAT 的密钥边界部署。

### 阶段 1：工程基础

- `npm run typecheck`、`npm test`、`npm run build` 可在 CI 执行。
- 本地 Long Polling 与生产 Webhook 两种模式可切换。
- `/healthz` 只检查进程，`/readyz` 检查 DB、Bot 配置和 `new-api` 契约。
- 数据库迁移可重复执行，服务支持优雅停机。
- 日志默认脱敏，并贯穿 `request_id`、`update_id`、`job_id`。

### 阶段 2：绑定与账户查询

- 实现私聊限定、Telegram ID 解析、失败统一提示、唯一绑定与解绑；admin 模式保留 UID 回退。
- 绑定关系定期复验；发现不一致立即停用。
- 完成四种额度显示类型的测试用例。
- 缓存只保存必要摘要，禁止缓存完整管理接口响应。

### 阶段 3：用量与订阅

- 时间窗口使用明确的起止时间戳并覆盖夏令时测试。
- 页面/消息分页不会超过 Telegram 消息长度限制。
- 空数据、被禁用账户、套餐过期和接口降级都有明确状态。
- Zod 契约变化会产生告警，而不是把缺失字段当 0 展示。

### 阶段 4：通知与客服

- 任务具备幂等 key，重复执行不会重复通知。
- 阈值通知具备触发、抑制、恢复状态机。
- 被用户拉黑后停止重试并标记 Telegram 用户不可达。
- 客服群回复只能路由到原工单用户，关闭后不能继续转发。

### 阶段 5：广播与管理

- 管理命令同时检查私聊/指定运营群和数字 ID 白名单。
- 广播必须预览与二次确认，确认记录写入审计日志。
- 发送速率可配置，遇到 `429` 按 `retry_after` 延迟。
- 可暂停、恢复和取消未完成广播，不重复发送已成功对象。

### 阶段 6：加固与上线

- 完成单元、集成、契约和 E2E 测试。
- 使用测试环境演练 `new-api` 超时、SQLite 锁等待、数据库短暂断开和 Telegram 429。
- 验证备份可恢复，不只验证备份文件存在。
- 配置错误率、队列积压、Webhook 延迟、绑定失败激增和通知失败告警。
- 形成部署、回滚、密钥轮换和事故处理手册。

## 4. 测试计划

| 测试层 | 重点 |
| --- | --- |
| 单元测试 | 额度换算、时间窗口、权限判断、通知状态机、错误映射、消息格式 |
| 数据库集成 | 唯一绑定、Update 去重、任务幂等、迁移前后兼容 |
| `new-api` 契约 | 对固定版本的脱敏 fixture 和测试环境验证 Zod schema |
| Telegram 集成 | Webhook secret、重复 Update、callback query、429/403/超时 |
| E2E | 从模拟 Telegram Update 到 Bot API 回复的完整链路 |
| 安全测试 | 越权绑定、用户枚举、日志泄密、管理员命令绕过、重放 |
| 负载测试 | 广播队列、批量通知、`new-api` 慢响应下的 Webhook 稳定性 |

覆盖率数字不能代替场景测试。核心权限、绑定和幂等模块建议分支覆盖率不低于 90%，普通展示代码不强求相同数字。

## 5. 发布计划

1. **内部测试**：只允许管理员和测试账号绑定，运行 2-3 天。
2. **灰度测试**：开放给 5%-10% 用户，观察接口负载、绑定失败率和通知误报。
3. **只读正式版**：开放账户、用量、订阅、通知和客服。
4. **规模化评估**：确认单实例 SQLite 的容量与备份恢复边界后，再评估迁移 PostgreSQL 与独立 Worker。
5. **全面开放**：审计、幂等、回滚和密钥轮换都完成演练后再放量。

回滚必须保留数据库向前兼容能力。发布新版本时先迁移、再滚动应用；删除字段或收紧约束至少跨两个版本完成。

## 6. 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 管理员 PAT 权限过大 | Bot 失陷可能扩大到后台 | admin 仅临时联调；生产改用 scoped bridge、网络隔离和密钥轮换 |
| `new-api` 接口随升级变化 | 错误展示或功能中断 | 固定兼容版本、Zod 校验、staging 契约测试、升级清单 |
| Bridge 尚未合入 fork | 无法做到无 UID 绑定 | 临时使用 UID + telegram_id 双向核对；先合入只读 Bridge 再正式放量 |
| 额度单位配置复杂 | 金额显示错误会造成客诉 | 每次读取公开状态配置，统一 quota formatter，覆盖四种模式 |
| 广播触发 Telegram 限流 | 大量失败或封禁风险 | 队列限速、遵守 `retry_after`、可暂停、分批灰度 |
| 轮询通知造成后台压力 | 用户规模增长后拖慢 `new-api` | 分页批处理、合理周期、缓存、事件/桥接能力替代高频轮询 |
| 修改 `new-api` 的许可证义务 | 发布和运维流程受影响 | `new-api` 为 AGPL-3.0；修改并网络提供服务前做许可证合规评估 |

## 7. 开发开始前的 Go/No-Go 条件

- 已确认机器人定位不是模型对话 Bot，或已明确另立范围。
- 已拿到 `new-api` 测试实例及版本信息。
- 已确认只读 Bridge 的路由、HMAC 和响应 DTO，并允许在 fork 增加对应 Go 代码。
- 已确认 Telegram Bot、域名和 Webhook HTTPS 入口归属。
- 已确定管理员白名单、客服群和数据保留要求。
- 已确认部署资源和密钥管理方式。
