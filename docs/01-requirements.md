# 产品需求

## 1. 产品定位

SuperTokenOverseas 是 `new-api` 中转站的 Telegram 自助服务与运营机器人。它解决的是用户不登录网页也能快速查看账户状态、接收额度提醒、读取公告和联系支持的问题。

本设计暂不把“通过 Telegram 直接与模型聊天”列入范围。那是另一类产品，会引入流式回复、会话存储、内容风控、模型选择和额外计费等需求。若实际目标包含模型聊天，需要单独立项，不能直接沿用本方案的工期。

## 2. 用户角色

| 角色 | 能力边界 |
| --- | --- |
| 游客 | 查看站点状态、公告、帮助和绑定入口 |
| 已绑定用户 | 查看自己的账户摘要、用量、订阅和通知设置，发起客服请求 |
| 运营人员 | 处理客服、预览和发送公告、查看机器人运行摘要 |
| 系统管理员 | 配置机器人、管理运营白名单、处理集成故障；不通过聊天消息直接展示系统密钥 |

运营和系统管理员身份必须由 Telegram 数字 ID 白名单确定，不能依赖 `@username`，因为用户名可以变更。

## 3. 首版范围（MVP）

### 3.1 普通用户功能

1. **开始与语言**
   - `/start` 展示主菜单。
   - 默认跟随 Telegram 语言，用户可以在设置中切换中文或英文。
   - 群聊中不展示账户信息，只引导用户进入机器人私聊。

2. **账号绑定**
   - 用户先在 `new-api` 网页完成 Telegram 绑定。
   - 用户在机器人私聊中提交自己的 `new-api` 用户 ID。
   - 机器人读取该用户资料，并核对资料中的 `telegram_id` 是否等于当前消息发送者 ID。
   - 校验成功后保存 `telegram_user_id -> new_api_user_id` 映射。
   - 解绑默认只删除机器人侧映射，不自动解除 `new-api` 的 Telegram 登录绑定。

3. **账户摘要**
   - 展示账户状态、用户组、总额度、已用额度和剩余额度。
   - 金额/额度显示必须读取 `new-api` 的 `quota_per_unit`、`quota_display_type` 和汇率配置，不能写死为美元。
   - Bot 不缓存或累计额度，`new-api` 是唯一账本。
   - 每次展示前或按缓存周期重新确认绑定仍有效。

4. **用量查询**
   - 支持今日、近 7 天、近 30 天三个固定时间范围。
   - 展示由 `new-api` 返回的总消耗、请求数；Bot 不保存模型维度或请求明细。
   - 所有时间边界按用户选择的时区计算，数据库统一保存 UTC 时间。

5. **订阅状态**
   - 展示当前生效套餐、周期、剩余额度和到期时间。
   - 购买、续费默认跳转网页，不在 Telegram 消息内处理支付资料。
   - Bot 不保存订阅、订单或支付状态副本。

6. **通知**
   - 用户可开启余额阈值、订阅到期和站点故障恢复通知。
   - 同一阈值事件只能通知一次，额度恢复后才允许再次触发。
   - 用户可一键暂停全部通知。

7. **公告与客服**
   - 展示当前公告并支持管理员主动广播。
   - 用户可以创建客服工单；机器人把消息转发到指定运营群，并只持久化回复路由映射，不保存客服正文副本。
   - 工单消息中只附带必要的用户 ID 和账户状态，不附带 API Key、PAT 或完整请求日志。

### 3.2 运营功能

- `/admin` 仅对白名单开放。
- 查看机器人健康状态、绑定用户数、最近任务失败数和消息积压。
- 创建广播草稿，按“预览 -> 目标人数 -> 二次确认 -> 限速发送”执行。
- 支持暂停广播，记录每个接收人的成功、失败及 Telegram 拉黑状态。
- MVP 不提供聊天内调整余额、封禁用户、删除令牌等高风险操作。

## 4. 暂不进入 MVP

- 在 Telegram 中直接展示完整模型 API Key。
- 收集或保存用户的 `new-api` 密码、面板 PAT。
- 在机器人内直接支付。
- 机器人直连或写入 `new-api` 数据库。
- 多个 `new-api` 站点的 SaaS 多租户能力。
- 大模型聊天、图片生成和提示词市场。
- 自动执行封号、扣费、渠道切换等运维动作。

## 5. 明确不做

- 机器人内兑换、充值、支付、退款、订单或额度调整。
- 创建、禁用、删除或展示用户令牌。
- 保存 `new-api` 消费明细、请求日志、订阅账本、订单或支付流水。
- 用户主动导出包含明细的用量报告。

## 6. 非功能需求

### 安全

- Telegram Webhook 必须校验 `X-Telegram-Bot-Api-Secret-Token`。
- 只接受私聊中的账号绑定和账户查询。
- 所有绑定、解绑、广播和管理员操作写入审计日志。
- 日志自动脱敏 `Authorization`、Bot Token、PAT、API Key、兑换码和支付参数。
- 管理凭据仅来自 Secret Manager 或部署环境，不写入数据库和 Git。
- 对 `/bind`、客服和管理员命令执行按 Telegram ID 的速率限制。
- 对 Telegram `update_id` 去重，防止 Webhook 重试导致重复执行。

### 可用性与性能

- Webhook 接收接口在 1 秒内完成持久化并响应，耗时任务进入队列。
- 查询请求外部依赖超时建议为 3 秒；只对幂等读请求做有限重试。
- Telegram 返回 `429` 时遵守 `retry_after`，不能立即循环重试。
- 首版目标：普通交互 P95 小于 2 秒（不含 `new-api` 故障时间），Webhook 月可用性目标 99.9%。

### 隐私与数据保留

- 仅保存 Telegram 数字 ID、语言、绑定关系、通知偏好、工单路由映射和白名单运营审计信息。
- 不因方便排障保存用户聊天全文；客服正文只存在于 Telegram 会话和运营群，不写入 Bot 数据库。
- 用户解绑后删除通知偏好并停止主动消息；审计数据按合规要求保留。

## 7. MVP 验收标准

- 未绑定用户无法查询任何账户资料。
- 用户 A 无法通过修改输入查询用户 B 的资料。
- `new-api` 中的 `telegram_id` 发生变化后，本地绑定会自动失效。
- 额度展示与站点后台在 USD、CNY、TOKENS、CUSTOM 四种配置下含义一致。
- 重复发送同一个 Telegram Update 不产生重复绑定、工单或广播。
- `new-api` 超时、返回 HTTP 错误、或返回 `HTTP 200 + success:false` 时都有明确且不泄密的用户提示。
- 广播发送前必须展示目标数量并二次确认，且可以追踪每条投递结果。
- 应用日志和错误上报中搜索不到实际 Bot Token、PAT 或用户 API Key。
